## Architecture Overview

### Tech Stack
- Python 3.13, **FastMCP** (MCP server framework), `httpx` for outbound HTTP, OpenTelemetry + Prometheus for telemetry, `python-dotenv` for local env config.

### Composite server pattern
`src/mcp_server.py` builds one `mcp_composite_server = FastMCP(...)` and **mounts** one sub-server per tool-domain file:

```
mcp_composite_server.mount(server=core_tools_mcp)
mcp_composite_server.mount(server=patient_management_mcp)
mcp_composite_server.mount(server=scheduling_tools_mcp)
mcp_composite_server.mount(server=encounter_management_mcp)
mcp_composite_server.mount(server=clinical_data_mcp)
mcp_composite_server.mount(server=clinical_support_mcp)
mcp_composite_server.mount(server=task_management_mcp)
mcp_composite_server.mount(server=communication_mcp)
mcp_composite_server.mount(server=billing_mcp)
mcp_composite_server.mount(server=intake_forms_mcp)
```
New tool domains follow this exact pattern: one new file in `src/tools/`, its own `<domain>_mcp = FastMCP(name="...")`, mounted with one added line here — **and** imported + added to `__all__` in `src/tools/__init__.py`. `mcp_server.py` pulls everything via `from tools import *`, so mounting alone isn't enough if the sub-server isn't also exported from `tools/__init__.py` — easy to miss, caught this exact gap when adding `billing_mcp`.

### Tool shape (the house convention — copy this for every new tool)
Every tool: `@<subserver>_mcp.tool` + `@with_tool_metrics()` decorators, first param `action: Literal[...]`, docstring with `<usecase>` and `<instructions>` XML tags (the `<instructions>` block documents required fields per action — this is what actually steers the LLM's calls), body pulls auth from `get_http_headers()` (`x-user-access-token`, `x-user-refresh-token`, `x-charmhealth-base-url`, `x-charmhealth-token-url`, `x-charmhealth-client-secret`, `x-charmhealth-accounts-server`), opens `async with CharmHealthAPIClient(...)`, then a `match action: case "...":` block per action. Each case: validate required fields (return a plain `{"error": ..., "guidance": ...}` dict if missing — no exceptions for user-facing validation errors), call `client.get(...)`/`client.post(...)` against a *relative* path (base URL + auth are handled by `CharmHealthAPIClient`), then attach a contextual `guidance` string to the response before returning (both on success — suggesting the natural next tool call — and on failure — explaining what likely went wrong). Best reference files: `tools/scheduling_tools.py` (`manageAppointments`) and `tools/encounter_management.py` (`manageEncounter`, which shows multi-endpoint composition in its `"review"` action).

### Auth flow
`CharmHealthAPIClient` (`src/api/api_client.py`) wraps `httpx.AsyncClient`, handles token refresh, and builds the `Authorization: Zoho-oauthtoken <token>` header per request. Per-user tokens arrive as HTTP headers (forwarded by the caller — cortex or a direct MCP client); falls back to the server's own `.env` credentials in stdio mode or when no headers are present.

## Known Pitfalls

- **No protocol-level `isError` yet:** every tool failure today returns a plain `{"error": "...", "guidance": "..."}` dict as normal *successful* content — there's no `isError`/`is_error` flag anywhere in `src/tools/`. Downstream consumers (cortex's `MCPConnector`) must check for the `"error"` key themselves; don't assume a failed call raises or gets flagged automatically. This is the exact gap cortex's ticket J13 is meant to close from the consumer side — a corresponding server-side upgrade is tracked in a separate plan doc, not in this repo yet.
- **`guidance` is a load-bearing convention, not decoration:** almost every tool attaches a `guidance` string to its response (success *and* failure) that nudges the LLM toward the next sensible tool call. Write these deliberately — they function like prompt engineering, not code comments. Skipping this on a new tool makes multi-step chaining worse for every agent that uses it.
- **Real API endpoint paths aren't documented in this repo:** every `client.get(...)`/`client.post(...)` call uses a relative path assumed to exist on the real CharmHealth backend. For new domains, those paths have to come from CharmHealth's actual API reference or a teammate who's touched that domain before — grepping this repo won't find them if the domain is new. See `docs/patient-billing-apis.md` for the billing + questionnaire endpoint reference, including which of several similarly-named endpoints is actually current vs. legacy.
- **HIPAA/PHI discipline:** this server can access real PHI. Never log PHI. Keep `COLLECT_METRICS=false` unless the telemetry backend is BAA-covered. Don't commit real credentials to `.env` or anywhere in git history.
- **Mutations need a cortex-side gating decision, not just an MCP-side implementation:** a new tool action that changes state needs a corresponding entry in cortex's mutation catalog (`approval/mutations/catalog.py`) to be gated correctly — building the tool here doesn't automatically gate it on the agent side. Status as of this writing: `managePatientBilling`'s `send_balance_reminder` and `manageIntakeForms`'s `share_sms`/`share_portal` are gated (STANDARD tier, added to cortex's catalog, grouped under "Revenue Cycle"/"Intake Forms" respectively). `managePatientBilling`'s `record_payment` is *deliberately* not exposed by the tool at all right now — pulled out of the `action` Literal and its case block entirely, not just left ungated — money movement, no settled gate tier and no revenue-cycle agent to test it through yet; there's a cortex-side tripwire test guarding against it silently reappearing in the catalog before the action itself comes back. `manageIntakeForms`'s `create_template` is a new mutation (creates real questionnaire templates on the practice's account) that is gated (STANDARD tier, "Intake Forms" group) — no clean inverse yet since the tool doesn't expose a `delete_template` action even though the real API has `DELETE /questionnaire/{id}`. Flag gating status explicitly whenever handing off a new mutating action.
- **The read-only actions also need an `action_class` entry in cortex's `policy.py`, or they log spurious warnings.** `_ACTION_CLASS_MAP` classifies every `(tool, action)` pair for receipt-building; anything unmapped falls through to `UPDATE` with a logged warning (safe default, but noisy and semantically wrong for a read). `managePatientBilling`'s `get_balance`/`list_invoices`/`get_receipts` and `manageIntakeForms`'s `list_templates`/`get_patient_forms`/`get_responses`/`get_responses_pdf` are all mapped to `READ` there — do the same for any new read action on these tools.
- **Cortex's `AgentConfig.tool_gates` is keyed by tool name, not action — don't reach for it to gate a single action.** A `ToolGate(tool_name="managePatientBilling", ...)` entry would gate *every* action of that tool for that agent, including the read-only ones (`get_balance`, `list_invoices`, `get_receipts`, or `list_templates`/`get_patient_forms`/`get_responses` for intake forms). The mutation catalog entry (tier-based, keyed by `(tool_name, action)`) is action-specific and is what actually gates `send_balance_reminder`/`share_sms`/`share_portal` today — no additional `ToolGate` was added for either tool, matching how most other mutations (`managePatientVitals/add`, `managePatientDrugs/add`, etc.) are gated. Only `manageMessages`, `submitClaim`, and `finalizeNote` carry an extra agent-level `ToolGate`, each for a specific reason — treat that as the exception, not the pattern to copy.
- **`managePatientBilling`'s `send_balance_reminder` endpoint — confirmed:** `POST /billing/statements/{id}/send` takes the `patient_id` directly in `{id}`; it is *not* a separately-generated `statement_id`, and there's no statement-listing/creation step needed first. This was previously unconfirmed (flagged with a `TODO(confirm with Vibhu)`); now resolved and reflected in the code.
- **Never wire `/patients/{id}/carddetails` into an LLM-facing tool action:** unlike `/patients/{id}/card_on_file` (display-safe, no token), `/carddetails` returns a raw, chargeable payment-gateway token. `managePatientBilling` briefly had a `get_card_on_file` action using the display-safe endpoint; it was deliberately pulled back out of scope pending a separate discussion, so the tool currently has no card-on-file action at all. If it's re-added, keep using `/card_on_file`, never `/carddetails` — charging a saved card is an explicit non-goal of this tool and would need its own ticket and security review.
- **`manageIntakeForms`'s `share_sms`/`share_portal` are NOT appointment-scoped:** the backend hardcodes `APPOINTMENT_ID = null` for both `/questionnaires/share/sms` and `/questionnaires/share/phr` — no client-side change here can tie a sent form to a specific visit. Appointment-tied questionnaire assignment only happens through `manageAppointments`'s `questionnaire` param on `"schedule"`/`"reschedule"` (writes a `PatientQuesMap` row with `APPOINTMENT_ID` set). Workflow: `manageIntakeForms(action='list_templates')` to discover a `questionnaire_id`, then pass it into `manageAppointments`'s `questionnaire=[{"questionnaire_id": ...}]` for the appointment-tied case.
- **Known bug, fixed:** `manageAppointments`'s `"reschedule"` case wasn't forwarding `questionnaire` or `consent_forms` into the request, even though `"schedule"` did and the docstring claimed reschedule supported both — a silent no-op (no error, the reschedule itself succeeded, the attachment just never happened). Now fixed in `scheduling_tools.py`: both fields are forwarded from `reschedule_data` the same way `schedule` does.
- **`client_secret`/`accounts_server` unbound-variable risk in the auth-header block:** the house pattern initializes `access_token`/`refresh_token`/`base_url`/`token_url` to `None` before the `try` that calls `get_http_headers()` — several existing files don't do the same for `client_secret`/`accounts_server`. If `get_http_headers()` raises (pure stdio mode, no headers at all), the exception is swallowed, but `client_secret` was never assigned, so the later `CharmHealthAPIClient(..., client_secret=client_secret)` call throws `UnboundLocalError`. Fixed in `billing.py` and `intake_forms.py` (both now pre-initialize all six auth vars to `None`). **Not yet fixed** in `manageAppointments`/`manageEncounter` (`scheduling_tools.py`/`encounter_management.py`) or other older tool files — same two-line fix applies there.
- **LLMs sometimes stringify array-typed tool parameters — design for it, don't just type-annotate against it.** Hit this with `manageIntakeForms`'s `create_template`: a calling model sent `questions` (typed `List[Dict[str, Any]]`) as a JSON-encoded *string* instead of a native array. FastMCP validates incoming arguments against the generated Pydantic schema *before* the function body ever runs, so a strict list-only type gets rejected at the protocol layer with a generic schema error — your own `{"error": ..., "guidance": ...}` convention never gets a chance to run or help the model self-correct. Best guess at why models do this: this same server already has a precedent for encoding list-like data as a string (`manageMessages`'s `recipient_member_ids`, documented as "comma-separated"), which likely biases models toward stringifying "list of things" params generally. Fix pattern: type the param as `Union[str, List[...]]`, and inside the function, `json.loads()` it if it arrives as a string (with a clear error if it doesn't parse to the right shape). Apply this to any future array/object-typed parameter, not just `questions`.
- **`manageIntakeForms`'s `create_template` enforces `notes_type` legality per `questionnaire_type` in code, against CharmHealth's actual Questionnaire Settings API reference doc.** The real API rejects illegal `notes_type`/`questionnaire_type` combinations (e.g. `"Section"` is not legal for `"Pre-screening Form"`) with an opaque `HTTP 400: Invalid value passed for notes_type`. The tool pre-validates against explicit legal sets for all three creatable types — `Feedback Form`, `Pre-screening Form`, `General Questionnaire` — sourced from the reference doc, not guessed. Two corrections from an earlier pass, once the reference doc was actually available: (1) `"Consent Form"` is **not** a real creatable `questionnaire_type` — the doc lists only the three above — so it was removed from `creatable_types` entirely; don't re-add it without re-confirming against the doc. (2) `comments` is a **required** field per the doc (previously treated as optional in this tool) — now enforced as required and always sent. `General Questionnaire`'s legal `notes_type` set is now the confirmed one from the doc's table (`Label`, `Simple Question`, `Question`, `Rating Scale`, `Question with Options`, `Question with Fixed Options`, `Date`, `Yes/No Question`, `Signature`, `Allergies`, `Medications`, `Supplements`, `Personal Details`, `Primary Contact Details`, `Primary Insurance Details` — note plain `"Rating"` is excluded, only `"Rating Scale"` is legal here). The doc doesn't mention `"Section"`, `"General"`, or several clinical widget types (`Chief Complaints`, `Symptoms`, `History of Present Illness`, `Past Medical History`, `Family History`, `Social History`, `Review of Systems`) for any of the three creatable types at all — treat those as unusable via `create_template` until proven otherwise, not just under-documented.
- **`manageFax` was removed (Zoho Desk ticket #1551594, 2026-08-06) — its endpoints aren't in CharmHealth's documented API surface.** Checked the full local API reference (`~/DeveloperLocal/CharmHealth-API-Documents/openapi.yaml`, 165 documented paths, plus every per-domain `EHR/`/`Billing/` doc): zero hits for `/fax` anywhere. The only "fax" matches at all are unrelated `fax` *fields* on other resources (Facility, Patient, Referral, Care Team, Recall — someone's fax number, not an endpoint). So `manageFax`'s `POST /fax/send` and `GET /fax/{fax_id}/status` were never confirmed against an actual API reference — unlike every other tool in this repo, which either has a documented endpoint or an explicit `TODO(confirm with Vibhu)`-style flag. Pulled the tool out entirely (function deleted from `communication.py`, removed from `tools/__init__.py`'s import and `__all__`, removed from the README tool list) rather than just leaving it ungated — same precedent as `managePatientBilling`'s `record_payment`. `communication_mcp` now exposes only `manageMessages`. To re-add: get the real endpoint paths confirmed against CharmHealth's actual API reference or a teammate who's used fax send/status, then re-add following the same house pattern.
- **A `label_style` field with the right keys but a wrong value *type* gets an opaque `HTTP 500 Internal Error` from the real API, not a `400`.** Bisected a repeated 500 on `create_template` down to `font_size` being sent as a JSON string (`"16"`) instead of a number (`16`) — every required key was present, so the earlier presence-only pre-flight check passed it straight through to the API, which failed ungracefully server-side instead of validating cleanly. Fixed: the pre-flight check for `"Label"` questions now also validates each `label_style` value (coercing an obviously-numeric `font_size` string to `int` rather than just rejecting it — matching the same stringification pattern already seen with `questions` — then checking `font_size` is `11-20` and that `font_weight`/`text_decoration`/`font_style`/`text_align` are each one of their documented enum values). Generalize this: a 500 (vs. a clean 400) from this API is a strong signal of a type/shape mismatch that passed a too-shallow local check, not necessarily a real backend outage.
- **`label_style` on `"Label"` questions is required by the real API but no longer required of the *caller* — this tool now defaults it.** The real intake-form UI is native (SwiftUI on Apple platforms), so these style hints have limited practical effect for our use case and forcing every caller to spell out all five sub-fields for a section header was pure friction. `create_template` now defaults any missing `label_style` (and any missing sub-key within a partially-specified one) to a plain look — `font_weight="normal"`, `text_decoration="none"`, `font_size=14`, `font_style="normal"`, `text_align="left"` — and only validates keys the caller actually supplied. Omitting `label_style` entirely on a `"Label"` question is now the expected/simple path, not an error.
- **FastMCP's protocol-level schema check on `create_template` is shallow by design — it does not catch a hallucinating model.** `questions` is typed `Union[str, List[Dict[str, Any]]]` specifically so the JSON-string-coercion trick works, which means Pydantic validates only that each item is *some* dict — it enforces nothing about which keys exist, their types, or their bounds. All of that (notes_type legality per questionnaire_type, conditional fields per notes_type, value types/ranges/enums, length/count limits) is hand-written pre-flight validation in the `create_template` case block, not automatic schema validation — treat it as the actual line of defense against a model inventing plausible-but-wrong content. As of this pass it now also enforces: every question has a `notes` string (3-20000 chars); `questionnaire_name` (3-100 chars) and `comments` (≤250 chars) length bounds; `questions` array size (1-200 items); `options` array size (1-100 items) and each item shaped `{"option": "..."}` (non-empty, ≤250 chars); `description` (Rating) labels each non-empty and ≤50 chars; `is_mandatory`/`is_multi_choice` coerced from a stringified `"true"`/`"false"` and type-checked otherwise. Any future conditional field on a new `notes_type` needs the same treatment (presence + type + range/enum + stringification tolerance) added here — the real API's error messages (opaque 400s and worse, opaque 500s) are not a substitute for this.
